# `house` — a migration repository for exercising pg_laswell

A toy household inventory: every physical thing in a house, what it cost, and
which room it is in. It exists to put pg_laswell through a full repository —
schema from nothing, reference data, seeds, and then the awkward changes that
come afterwards — against a real PostgreSQL, and to check afterwards that the
database says what the specifications claimed.

Fifty-one signed specifications, 118 intents, 26 of the intent kinds this build
implements. Ten dependency levels, and the concurrency inside them is derived
by pg_laswell rather than declared here.

## Running it

```bash
bin/setup.sh --port 5555      # roles, database, ledger, signing key, laswell.ini
bin/sign-specs.sh             # canonical bytes from getSpecDigest, signed with openssl
bin/run.sh                    # status, dry run, apply, verify
```

`bin/setup.sh` **drops and recreates** the `house` database and the
`house_runner` and `house_app` roles, so it is a reset as much as a setup. It
must be run by a superuser; everything after it runs as `house_runner`, which
owns the application schema and has `SELECT` and nothing more on the trust
tables. That separation is the point of the bootstrap script and is not
decoration: a role that owns `laswell.trusted_key` can insert into it, and the
trust gate would then exist only as a comment.

`bin/run.sh --status` and `bin/run.sh --dry-run` stop after that step. Exit
codes come straight from `pg_laswell`, so a pipeline can branch on them without
parsing output: 0 nothing pending, 1 refused or failed, 2 a repository problem,
3 a configuration problem.

Nothing in `keys/` or `laswell.ini` is committed. Both are regenerated by
`bin/setup.sh`, and both are mode 0600 — `laswell.ini` holds a password *and*
declares which signing keys are trusted, which is the same rule `~/.pgpass`
lives under.

Nothing in `keys/` or `laswell.ini` is committed, so the `signatures` block in
each committed specification was made with a throwaway key nobody else has and
will verify nowhere. That is why `bin/sign-specs.sh` is a step rather than a
convenience: it re-signs every specification with the key `bin/setup.sh` just
generated, and on a fresh clone that shows up as a diff on all fifty-one files.
Expected, and the only honest arrangement — the alternative is committing a
private key so the signatures look meaningful.

## The model

One schema, `house`. Every physical thing is a row in `house.item`, which
carries the four facts every category shares — what it is called, what it cost,
when it was bought, which room it is in — and a `category` saying which detail
table carries the rest:

```
                      house.room ──┐         ┌── house.brand
                                   │         │
                                 house.item ─┘
                                   │
     ┌──────────┬──────────┬───────┼────────┬──────────┬──────────┐
 furniture  kitchenware electronics  book   food  cleaning_product tool
     │                                │
     └── parent_item_id (self) ───────┘ shelf_item_id
```

Each detail table's primary key *is* its foreign key to `house.item`, which is
what makes the pair exactly one-to-one. Two links inside the model are worth
naming, because they are the ones the domain actually has:

- `house.furniture.parent_item_id` points at `house.furniture`, so the six
  dining chairs belong to the dining table and not to a saucepan.
- `house.book.shelf_item_id` points at `house.furniture`, so a book can only be
  shelved on something that is furniture.

Eight enums, four identity columns (all `GENERATED ALWAYS`), sixteen check
constraints, twelve foreign keys — every one of them with an index leading with
the referencing column — three views, one materialized view, and a
`touch_updated_at` trigger on the four tables that have an `updated_at`.

Conventions follow the house style: `snake_case`, `bigint GENERATED ALWAYS AS
IDENTITY` rather than `serial`, `timestamptz` never `timestamp`, `NOT NULL`
unless absence means something, and a `COMMENT ON` for every object. There is
no `tenant_id` and no row-level security: a house has one household, so nothing
here is tenant-scoped, and inventing a tenant column to satisfy a rule about
multi-tenant tables would be a column nobody could ever filter on.

## About `depends_on`

Every edge in this repository is one the change actually has: a table on the
enum its column uses, a foreign key on the table it points at, a seed on the
reference rows it names. Nothing is chained merely because it is numbered
later. Three edges look like padding and are not:

- **`0093-color-extra` depends on `0072-seed-color`.** The seed writes explicit
  colour ids; the `COPY` lets the identity column generate them. Run the other
  way round, `COPY` would take ids 1 to 6 and the seed's explicit ids would then
  collide. The dependency is a primary key, not a preference.
- **`0095-price-backfill` depends on all seven item seeds.** A backfill against
  an empty table succeeds having done nothing — and would be marked applied and
  never listed pending again.
- **`0099-rename-borrower` depends on `0096-lend-books`.** `0096` names
  `borrowed_by`, which `0099` renames. A rename that landed first would leave
  `0096` unable to parse.

`0100-grant-app` depends on every table and view specification, which looks
defensive and is not: `GRANT … ON ALL TABLES IN SCHEMA` reaches the tables that
exist when it runs and no others.

The result is ten levels rather than a chain of fifty-one, and pg_laswell finds
groups of up to eleven inside them. It also refuses concurrency more often than
the graph alone would suggest, for two reasons it states in its own output —
the detail tables all carry foreign keys reaching `house.item`, `house.room` and
`house.brand`, which is a shared relation and provable; and once
`touch_updated_at` exists, a table carrying it can no longer be *proved*
independent of anything, because what a trigger function writes is not visible
in the catalog. Both refusals are correct. The second is the interesting one:
the tool says "independence is NOT proven … your call" rather than guessing.

## Things this repository found

Each of these came out of writing the specifications, and each is left in the
repository as the shape that works rather than papered over.

1. **`create_trigger.function` is emitted verbatim**, so it needs the argument
   list: `"house.touch_updated_at()"`, not `"house.touch_updated_at"`. The dry
   run caught it as a syntax error before anything ran.

2. **`create_table`'s inline `PRIMARY KEY` is invisible to later intents in the
   same specification.** The projection records columns but leaves `indexes`
   empty, so a foreign key added a few intents later warns that no index leads
   with its referencing column when the primary key is exactly that index. A
   warning, not a refusal — but it is a false one, and every detail table here
   raises it.

3. **`create_materialized_view` is likewise invisible to a later `create_index`
   in the same specification**, which refuses outright rather than warning.
   `0064` exists because of this: the index is split into its own specification,
   which is a real dependency and reads honestly, but the split is forced.

4. **`drop_view` does not update the projected observations at all**, because
   `apply_projection` keys on `schema + "." + table` and a `drop_view` intent
   carries `name` rather than `table`. The visible consequence: a `drop_view`
   followed by `replace_view` in one specification takes the "already exists"
   branch, so `replace_view` skips its `COMMENT ON VIEW` and the view comes back
   undocumented. `0099` carries an explicit `set_comment` to put it back. The
   same key mismatch is documented as fixed for the *conflict* keys in
   `planner.h`, so this looks like the projection half of that bug.

5. **The rewrite classifier compares type strings, not types.** `varchar(120)`
   against an observed `character varying(60)` falls through to "assume a
   rewrite"; writing the type as `character varying(120)` proves the
   no-rewrite case and drops the warning. Same DDL either way — only the
   verdict changes.

6. **`CREATE OR REPLACE VIEW` cannot rename an output column**, which is what
   makes `0099` cost a drop and rebuild rather than a replace. pg_laswell warns
   about it *and* the dry run refuses the plan that ignored the warning, which
   is the pair working as advertised.

7. **Floating-point values are refused anywhere in a specification.** Every
   `numeric` in the seeds is written as a string. That is the intended
   behaviour, and worth knowing before writing a seed by hand.

8. **A killed `pg_laswell` wedges the repository.** Interrupt an apply — Ctrl-C,
   or a `| head` that closes the pipe — and the job it was running keeps
   `finished_at NULL` forever. `applied_index()` reads any unfinished job as
   `running`, so the spec stays `in_progress` and everything downstream of it
   reports `depends_on … which is in_progress -- not applied and not runnable`,
   exit 2. The manual documents the detection that would settle it — *"a job
   with no finished_at whose advisory lock is absent from pg_locks died with
   its connection"* — and the repository scan does not apply it. `bin/unwedge.sh`
   does, as a single UPDATE.

9. **A failed migration is never retried, and the run still exits 0.** This one
   follows from the last and is the sharper of the two. `repository.h` treats
   `failed` as runnable — it is in the pending set at line 516 and a runnable
   dependency at 554, and it is placed in the level plan. `deploy.h` then
   selects on `status == "pending"` alone (lines 122 and 158), so a `failed`
   entry is printed in the plan, never started, not counted, and the deployment
   exits 0 having skipped it. Observed here: after `bin/unwedge.sh` marked the
   interrupted job failed, `--status` printed `0 pending` and, on the line
   below, `level 1: 0062-view-borrowed-book`.

   A second consequence of the same split: the closing `applied N migration(s)`
   is the *pending count*, not the number of jobs that ran (`deploy.h:169`), so
   the run that skipped `0062` still claimed to have applied it. `bin/unwedge.sh`
   therefore clears the whole failed job row rather than marking it failed, so
   the spec classifies as `pending` and actually runs.

Two more observations that are not defects. `insert_rows` into a `GENERATED
ALWAYS AS IDENTITY` column needs `"overriding": "system"` and is refused
without it; the `setval` that follows is emitted from the table's own contents
at execution time, so re-running a partly applied seed still lands correctly.
And `copy_rows` has no `overriding` key at all, which is why `0093` lets the
identity column generate its ids.

## Verifying

`sql/verify.sql` runs 45 assertions and stops on the first failure. It checks
structure (table, view and enum counts; that every table, column and enum
carries a comment; that every identity column is `GENERATED ALWAYS`; that no
foreign key column is missing its leading index), the data (row counts per
category, the supertype and detail tables agreeing in both directions, the six
chairs pointing at their table, the twelve books on real shelves), the effect
of each evolution migration, the grants, and the ledger.

`bin/run.sh` runs it last. It can also be run on its own:

```bash
PGPASSWORD=$(sed -n 's/^password *= *//p' laswell.ini) \
  psql -h 127.0.0.1 -p 5555 -U house_runner -d house -v ON_ERROR_STOP=1 \
       -f sql/verify.sql
```

## Layout

```
bin/setup.sh        drop and rebuild the database, roles, ledger, key and config
bin/sign-specs.sh   sign every spec in migrations/ (idempotent)
bin/run.sh          status, dry run, apply, verify
bin/unwedge.sh      recover a repository left wedged by an interrupted apply
migrations/*.json   the repository: 51 signed specifications
sql/verify.sql      45 assertions about what the repository produced
keys/               generated; not committed
laswell.ini         generated; not committed; mode 0600
```
