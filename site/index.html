Migrations that refuse what they cannot prove.

pg_laswell plans a schema change against the live catalog, tells you what it will do and why, commits when the database asks rather than on a timer, and records every statement it ran. It refuses anything it cannot justify from a reading — and names the reading.

What you are buying into

Every one of these is a decision the tool makes from a measurement, not a preference it was configured with.

What ran is what you were shown

A plan carries a digest over its statements, the reasoning behind each one, the locks each takes, and the refusals. startMigration recomputes it and must agree. The receipt covers what will run — never the server's load at that instant, which is measured again precisely because it goes stale.

It commits when the database asks

A paced change commits on a lock waiter, on an interval, or on a row cap — whichever comes first. Measured on 300 000 rows with an application contending: 48 of 63 commits fired on a waiter and zero on the interval, finishing in the same wall time as an uncontended run. Committing on contention rather than on a schedule costs nothing and bounds the harm.

It refuses, and names the measurement

A MERGE keyed on a column with only a composite unique index is refused: measured on 18.6, one source row updated two target rows with no error and nothing in the row count to notice. A paced MERGE on PostgreSQL 15 or 16 is refused because MERGE … RETURNING is a syntax error there — measured against real clusters, not read off a release note.

The database decides what may run

The trust root, the environment label and the release approvals live in tables the migrating role can read and cannot write. A permissive client configuration cannot talk a production database into accepting a development migration.

It measures harm it is causing

An observer counts the transitive waiters queued behind the migration — a direct-blocker count sees 1 where the real pile-up is 6 — throttles, pauses, and cancels a statement that starves a waiter past its limit. The migration stops; the application does not.

No agent in the deployment path

pg_laswell applies a repository and exits with a code a pipeline can branch on. The MCP server is for authoring a migration, not for running one. Nothing about the safety decisions needs a model at four in the morning.

One repository, several databases

A change is always single-database — PostgreSQL has no cross-database transaction, so a change spanning two would be atomic in neither. A change may require a change on a different database, and that is what depends_on is for. It crosses databases freely; each database keeps its own ledger, so “has that been applied” is answered where it ran.

Four specifications, two databases, one dependency that crosses between them. pg_laswell applies 0030 on store and holds 0040 until that is recorded applied in store's own ledger — then applies it on audit. Neither database can see the other's tables; only the dependency crosses.

pg_cron is drawn outside the repository on purpose. pg_laswell holds that a migration is a change to schema state applied exactly once: the ledger keys on the specification digest, and a digest that has succeeded is never listed pending again. Rotating a partition every night runs repeatedly, so it is not a migration and pg_laswell will not pretend to own it. Creating the partitioned table, attaching a partition once, and building the publication are structural changes applied once — those are migrations.

Any-to-any, not just a pair

The dependency graph is global and the ledgers are local, so the shapes a deployment can express are whatever the graph can draw.

Each arrow is a depends_on between specifications on different connections. A cycle in the dependency graph is refused by name — pg_laswell reports which specifications form it — so a replication ring is expressed as the acyclic order that builds it, not as a cycle in the repository.

The audit table is the one you already know

The history database holds audit.logged_actions in the shape the PostgreSQL wiki's audit trigger has used for years — so the rows mean what your existing queries expect them to mean. 

{
  "laswell_spec_version": 1,
  "id": "0040-subscription",
  "description": "Consume the store's audit log into the history database.",
  "rationale": "The store keeps a rolling window; audit keeps everything.",
  "target": { "connection": "audit", "environment": "production" },
  "depends_on": ["0030-publication"],
  "intents": [
    {
      "kind": "create_subscription",
      "name": "audit_from_store",
      "connection": "service=store_publisher",
      "publications": ["store_audit"],
      "comment": "Full history of every row change in store."
    }
  ]
}

The connection inside the intent is the libpq string the SUBSCRIPTION itself dials out on — a PostgreSQL concept. The target.connection above it is which database pg_laswell applies this specification to. A credential is refused rather than redacted here: the ledger records what ran, and a redacted ledger entry would no longer be what ran. Name a service instead.

Every idea the tool has, in one place

pg_laswell has a small vocabulary and uses each word for exactly one thing. Most confusion about migration tools comes from words that mean four things at once, so here is each of them and what it actually is.

What you write

specification
A signed JSON document: an id, a description, the reasoning, a target, and the changes it asks for. Nothing else in the file is signed, which is what lets an optional key be added later without invalidating anything already written.
intent
A declared outcome, never SQL. {{KINDS}} kinds, from create_table to merge_rows to attach_partition. You say what should be true; the planner decides how, from what it measures.
digest
SHA-256 over the canonical bytes (RFC 8785). The short form is what a human quotes in a ticket.
signature
Detached Ed25519. A key id is the content address of the key itself, so an id can never be reassigned to different bytes.
depends_on
Ordering that no measurement can derive, because it is business sequence rather than a fact about the schema. It crosses databases and directories, and it is satisfied by the ledger — if the database says it ran, the file need not be present.
target
Four different jobs people usually conflate. connection routes; database and environment guard; epoch scopes; min_server_version refuses. All inside the signature, so none can be edited on the way to production.
release
A tag a specification carries and a database approves. Until somebody with the privilege to do it says that tag is ready here, everything carrying it waits.

Where specifications live

source
One directory of specifications. Usually one project's.
repository
The union of the sources a deployment names. Ordered as a single graph, so a dependency crosses freely between them — and an id claimed by two of them is refused rather than resolved, because depends_on names an id and nothing else.
manifest
A file naming those sources, giving each a name that messages use in place of its path. Its complete flag is an assertion no single directory can make about itself: these are all of this database's story.
status
What a listing says about each specification: pending, applied, in progress, failed, modified after apply, or one of the not-for-here answers — wrong database, wrong environment, held for a release, held for an epoch, retired epoch. None of the last five is an error.
problem
A fault of the repository rather than of any one migration: drift, a file that will not parse, a dependency nothing can satisfy. One is enough to stop the whole run, because what is unknown includes where the unreadable file sat in the order.

What the database holds

ledger
A schema in the target database, versioned, that records what ran. It never stores a file path — which is exactly why several directories can be read as one repository, and why a spec's identity survives being moved.
trust root
The table of signing keys this database accepts. It is a foreign key, not a code path: an untrusted signer cannot create a row at all. A permissive client config cannot talk a database into anything.
environment
One row, enforced by the primary key. Two rows would make “which environment is this” a question with two answers, and every gate downstream would have to pick.
epoch
A lineage of tracked history. It is what lets a deployment answer for part of a database — see below. Opened by whoever owns the schema, never by the deploying role, because opening one narrows a safety check.
job & step
One attempt to apply one migration, and every statement it ran. The plan is stored as it was shown, not regenerated afterwards.
cursor
Where a paced backfill got to. Committed with the batch, so a job that dies resumes instead of starting over.

What the planner produces

observation
What was measured before deciding: table sizes, the catalog, who is waiting on a lock, how much connection headroom the server has. Every decision names the reading behind it.
plan
Ordered steps, each with the SQL, the reason, the lock it takes and the settings it needs — plus warnings, conflicts, and prerequisites.
plan digest
How “what ran is what you were shown” becomes checkable rather than promised. Readings that change under the plan's feet, like when autovacuum last touched the statistics, are shown but deliberately not hashed.
prerequisite
Work the tool will not do for you, named with where to do it and how to check it is done. A half-filled one is worse than none.
dry run
Every pending plan tried against the real schema in a transaction that is rolled back. Per specification, and that is a real limit: one that needs a table an earlier pending specification creates cannot be planned yet, and says so. A repository-wide dry run is not possible — paced batches commit by design, and an index built concurrently cannot run in a transaction at all.

How it runs

pacing
Work in batches that commit when the database asks: a lock waiter appears, an interval elapses, or a batch cap is reached. Measured on 300 000 rows under contention: 48 of 63 commits fired on a waiter, zero on the interval, in the same wall time as an uncontended run.
observer
A separate connection counting who is blocked — transitively, because a direct-blocker count saw 1 where the real blast radius was 6. It throttles, pauses, and can cancel the statement.
advisory lock
One per specification and one per table it touches. The last word on safety: an overlap the grouping wrongly permitted is refused here, so a wrong call is refused rather than corrupting.
budget & gates
How many jobs and operations may run at once, derived from the server's own capacity rather than guessed.

How it decides what is safe

relations touched
Three sources: what each intent names, what PostgreSQL itself resolves in the rendered SQL, and foreign keys in both directions. Triggers are named, never resolved — a function body is opaque, so a target carrying one is reported rather than silently treated as understood.
concurrency
Levels and groups. The asymmetry is the whole design: a conflict is decidable, independence is not. So incomplete evidence denies concurrency and hands you the decision.
drift
Two kinds. A specification edited after it was applied — the database no longer matches the file claiming to describe it. And a migration applied here that no file describes.

Ways people actually run it

The same binary and the same ledger, arranged differently. Each of these is a configuration, not a mode — there is no flag that switches pg_laswell between them.

flowchart LR

Specifications carry a tag and wait. Approving it is a privileged statement in the target database, recorded with who and when. The tag is inside the signature, so it cannot be retargeted on the way to production.

Rolling the baseline forward

flowchart LR
  B1["base backup"] --> EA["epoch A"]
  EA --> B2["new base backup"]
  B2 -->|"retire A"| EB["epoch B"]
  EA -.->|"still applied"| EB

One lineage holds every change since the last base backup. A new backup is taken, that lineage is retired, and the next one begins. Retiring stops tracking without unsaying that anything ran.
